# Data

Inputs the simulation reads, and outputs it writes. They were one flat folder,
which meant a generated result sat beside a hand-maintained map with nothing to
say which was which — and it would only have got worse once traces started being
exported here.

```text
data/
├── maps/        road networks           input,  committed
├── demand/      parameter/curve tables  input,  committed
├── scenarios/   complete seeded runs    input,  committed
└── results/     generated output        output, mostly ignored
```

The rule: **anything under `results/` can be deleted and regenerated.** Nothing
else can.

## maps/

A road network: `intersections`, `roads`, and optionally `buildings`. Loaded by
`JsonMapLoader`, or `CsvMapLoader` for the one CSV.

| File | What it is |
|---|---|
| `district1_network.json` | The only map. 389 junctions, 730 directed roads, 1162 buildings and 243 land-cover polygons, generated by `tools/generate_osm_map.py` from OpenStreetMap. |

Despite its historical filename, this is **not the whole former District 1
area**. Since 1 July 2025, `District 1` / `Quận 1` is also a familiar
historical-geographic label rather than a current district-level administrative
unit. The generator uses the bounding box `(south=10.7685, west=106.6905,
north=10.7825, east=106.7085)`, an approximately 3.05 km² study window in the
**former District 1 area**. The old District 1 administrative overview reports
7.7211 km² as a historical baseline, so the file must not be described as a
district-wide network or census. See
[`docs/DISTRICT1_SCENARIO.md`](../docs/DISTRICT1_SCENARIO.md) for the
administrative-name note and sources.

The counts above are **DATASET FACTS**: they describe this committed JSON file,
not the real number of roads, junctions or buildings in the former District 1
area. The OSM snapshot date is not embedded in the map, and 885 of its 1162
buildings are typed `OTHER`; neither coverage nor building use is complete
enough for population forecasting.

Road occupancy is runtime state. On scenario initialization and reset, the
simulator clears legacy `currentVehicleCount`, density and congestion values,
reopens non-closed roads, and preserves explicitly `CLOSED` roads. The map
generator now also writes zero dynamic traffic by default. This prevents
invisible persisted vehicles from consuming capacity.

The hand-made toy maps that used to sit here — `small_city`, `congestion_demo`,
`accident_demo`, `density_demo` — are gone. None had buildings or land cover, so
none could carry a demand-driven scenario, and keeping them as "scenarios" in
the picker suggested otherwise. The routing benchmark now measures this former
District 1 study window instead of a six-junction sketch.

`sample_map.json` and `sample_map.csv` moved to `src/test/resources/maps/`. They
are three-junction fixtures proving the JSON and CSV loaders agree, which is a
test concern, not project data.

## scenarios/

A run definition: map, clock, seed, scale, generated `demandSources`, events,
and optional scripted vehicles. The same shape is accepted by
`POST /api/simulation/initialize`, except activation also follows the scenario's
map reference.

`district1_typical_day.json` is the bundled default:
**Central District 1 - Synthetic Weekday**. It combines generated demand with
four scripted warm-start vehicles, because the first generated departure is at
272.10 simulated seconds and a demo should not begin with an empty map.

Its fixed acceptance snapshot is:

| Measure | Seeded result |
|---|---:|
| Generated plans | 216 |
| Structural generation failures | 0 |
| Generated motorcycles | 184 |
| Generated cars | 32 |
| Scripted vehicles present at `t = 0` | 4 |

These are **DETERMINISTIC MODEL OUTPUTS**, not observed traffic counts. They
hold for the committed map, scenario, parameter table, demand algorithm and
seed `20260728`. See
[`docs/DISTRICT1_SCENARIO.md`](../docs/DISTRICT1_SCENARIO.md) for the evidence
classification, zones, flows and limitations.

## demand/

`default_assumptions.json` supplies every building-type occupancy/attraction
parameter, the gravity distance-decay factor, and normalized 24-hour departure
curves. Its top-level status and note explicitly mark the table as an assumption
so later calibration is a data replacement rather than a Java change.

The words are intentional:

- **DATASET FACT** describes a value measured from the committed repository
  data or a deterministic run.
- **CITY-LEVEL PROXY** describes external Ho Chi Minh City evidence used only
  to choose a plausible shape or order of magnitude. It is not former
  District 1 study-window calibration.
- **SYNTHETIC ASSUMPTION** describes an authored input such as occupancy,
  production, modal mix, dwell time, hourly curve, gravity decay or `scale`.

No bundled demand parameter is an observed estimate for the former District 1
study window, and the scenario is neither a calibrated model nor a traffic
forecast.

## results/

Generated. `experiment_results.json` is the one committed file here, because it
is the published routing baseline that `EXPERIMENT_RESULTS.md` quotes and
`ExperimentService` compares against; regenerate it with:

```bash
mvn -q exec:java -Dexec.mainClass=team.traffic.experiment.ExperimentRunner -Dexec.args=--write
```

Everything else written here is ignored by git — see `.gitignore`. That is where
exported traces belong: a trace is a recording of one run, it is large, and it
is reproducible from the map, the scenario and the seed, so committing it would
add weight without adding information.

Suggested naming when trace export lands, so runs stay sortable and
self-describing:

```text
results/traces/<map>-<scenario>-<yyyymmdd-hhmm>.json
```
