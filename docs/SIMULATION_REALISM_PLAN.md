# Simulation Realism: Implemented Scope and Limits

This file used to be a future-work plan. The renderer, OSM enrichment, clock and
demand workstreams are now implemented, so it is retained as a status record
and an honest boundary around what the simulation can claim.

## Current status

| Area | Implemented |
|---|---|
| Renderer | One world-metre Pixi container, pan/zoom, sprites, readable palette, buildings, land cover, signals and lane markings |
| Physical motion | Backend-resolved poses, authoritative building access links, continuous lateral offset, topology-aware lane and junction interpolation |
| Map | District 1 study-window roads, directed geometry, lane count/width, buildings and access intersections |
| Time | `SimulationClock` with scenario start time and time-of-day publication |
| Demand | Seeded building/zone demand, hourly curves, multi-leg plans, dwell time, return/removal policies and runtime spawning |
| Replay | Immutable frame history keyed by `timelineId` and `frameId` |

The detailed renderer contract is in `PHYSICAL_VIEW_PLAN.md`. Demand semantics
are in `DEMAND_AND_SCENARIO_DESIGN.md`; the shipped case study and its evidence
labels are in `DISTRICT1_SCENARIO.md`.

## What is physically simulated

- Directed routing over the movement graph.
- Per-lane longitudinal occupancy, car following and entry-space checks.
- Gradual lateral movement and motorcycle filtering rules.
- Stop-line arbitration, traffic-signal phases and junction priority.
- Timed traffic events, road/lane obstruction and collision detection.
- Demand departures and resolved multi-leg trip lifecycle.

The backend owns these decisions. Frontend interpolation is presentation only.

## What is derived or synthetic

- Missing OSM lane values use road-class defaults.
- HOUTRANS-derived production/purpose/internal-outbound ratios and one digitized
  hourly curve, plus the 2024 registered-stock vehicle ratio, are historical or
  citywide proxies rather than current calibration.
- Building occupancy/attraction, purpose-specific curves, dwell ranges, cordon
  volumes/shares, gateway allocation and scenario scale are explicit
  assumptions.
- Building production uses footprint area. Storeys/floor area and occupancy
  survey data are not available.
- Default signalisation and phase timings are generated by the simulator rather
  than imported from a surveyed controller plan.
- The District 1 scenario has no scripted warm-start traffic; every vehicle is
  attributable to one exact seeded demand plan. A five-minute microscopic
  initialization pre-roll creates the first populated 06:05 frame without
  retaining artificial fast-forward history.

The 39,434-plan / 71,267-leg output is an explicit microscopic sample against a
documented historical 0.4–0.7 million-leg/day proxy envelope. It is therefore a
deterministic educational scenario, not a calibrated traffic forecast or
evidence of current District 1 traffic volume.

## Map-generation boundary

`tools/generate_osm_map.py` uses a bounded Overpass extract and keeps stable
`W<wayId>-<segment><direction>` road IDs. It emits:

- the largest connected supported-road component;
- directed roads with name, physical-road ID, geometry, lane count and width;
- building footprints, type and a bounded nearest-junction access point;
- land-cover polygons.

Buildings without a road access point inside the configured cap are dropped.
The script reports OSM-versus-inferred lane provenance during generation. The
committed schema does not yet carry that provenance per road.

Normal regeneration accepts only an OSM base timestamp no more than 24 hours
old and replaces cache files atomically; stale/legacy caches require explicit
`--offline-cache`. The final audit checked all 439 source ways. The committed
730 directed roads represent 560 physical segments: 390 one-way (380
`oneway=yes`, 10 roundabouts) and 170 represented both ways. Among 168
one-way segments with at least three lanes, 155 have direct OSM tags and 13 use
inference/defaults. Eleven motorcycle-specific reverse exceptions remain
unsupported by the all-vehicle graph.

Runtime occupancy is never map data. Generated roads now start with vehicle
count, density and congestion equal to zero; simulator configure/reset also
clears legacy dynamic values while preserving explicit `CLOSED` roads.

## Known model limits

1. **No timed connector occupancy.** A crossing is authorized by the backend,
   but it moves from the incoming to outgoing road within a sub-step. Pixi draws
   the connector between those frames; it does not make that animation a second
   physical truth.
2. **No calibrated OD matrix or counts.** The gravity/zone model is useful for
   repeatable behaviour and software testing, not traffic prediction.
3. **No floor-area model.** A tower and a low-rise block with equal footprints
   receive equal base area before type factors.
4. **No pedestrians or bicycles.** Their conflicts, crossings and mode choice
   are absent.
5. **No scheduled public transport.** Buses are vehicles, not a timetable,
   passenger-demand or stop-dwell system.
6. **No live network synchronisation.** The committed map is a reproducible
   generated artefact, not a live OSM mirror.
7. **Full-map static Physical View.** The current District 1 geometry is
   retained as one static scene, while vehicle/signal requests and sprite
   submission are camera-bounded. Larger maps need tiled static geometry as
   well.

## Next work, if the project continues

Priorities should be evidence-driven:

1. Add instrumented frame-time and state-payload benchmarks before further
   renderer changes.
2. Add explicit junction-connector progress only together with reservation,
   collision and deadlock semantics.
3. Persist lane-data provenance and building levels in the map schema.
4. Calibrate demand against a documented OD/count dataset, with separate
   training and validation checks.
5. Add a surveyed signal inventory before claiming real controller behaviour.

Those are model changes, not submission fixes; each would need new validation
data and regression tests.
